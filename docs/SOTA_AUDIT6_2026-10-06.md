## 3. Verdict per claim

### N1. Multi-level fork of GPU-visible KV state across processes (extent chains)

**Verdict: PARTIALLY TAKEN.**

- **Closest work:** Omni-Flow (arXiv 2606.31093) across processes, and the
  in-process trees of vLLM and SGLang for the structure.
- **What is taken.**
  - The structure, in one process, since 2023: vLLM shares blocks at every
    level of a beam ("similar to the process tree in the OS created by
    compound forks") and frees them by reference count; SGLang's radix tree
    keeps "common ancestors" shared; ForkKV, KVTether, AAFLOW+, Parrot, and
    Symphony's `kv_fork` ("forking recursively if needed") repeat it.
  - Across processes without a copy, in device memory on one GPU: Omni-Flow
    publishes KV pages after each inference, keeps a "session's page chain"
    named by "Chained Paged Hashing", lets same-device consumers bind an
    alias, and copies a partial page when it is extended.
  - Across processes with a copy: chunk chains in LMCache, the shared host
    pools of Section 16, the CXL regions.
  - As an OS structure: IO-Lite's buffer aggregate, "an ordered list of
    <pointer,length> pairs" over immutable buffers that are mapped read-only
    into each domain.
- **Exact difference.** In the opened set no work composes one contiguous KV
  tensor of a GPU-serving process from several segments that different OS
  processes published as host files, with the GPU reading every segment in
  place through host page tables. Omni-Flow needs a memory manager, a slot
  engine, and Redis, lives in device memory, and is bound to one GPU. The
  in-process trees end at the process boundary.
- **What remains claimable:** chains of published extents between OS
  processes by host mapping, across the two MIG instances, with no manager.
  It is an increment over the one-level extents of Section 16, and a
  reviewer will read it as the radix tree of SGLang rebuilt out of files.

### N2. Write protection of shared GPU-visible state by the host MMU on the GPU access path

**Verdict: PARTIALLY TAKEN.**

- **Closest work:** onnx-genai issue #777 (write-protected shared KV prefix
  pages in device memory, one process, tested), and The Ingestion Tax for
  the host-mapping fact.
- **What is taken.**
  - Device memory does offer read-only mappings. `CU_MEM_ACCESS_FLAGS_PROT_READ`
    is supported since CUDA 12.0 (Features Archive). Liu et al. use a write
    into such a mapping as a fault-injection case on A6000 to H100. This
    project's own probe (Section 17, item 3) saw the read-only access
    enforced on Thor.
  - The idea "protect the shared KV prefix with page protection so a write
    faults instead of corrupting another sharer" is written in onnx-genai
    #777 and implemented as an allocator primitive with a passing test, for
    sequences of one process.
  - A GPU store into a read-only host mapping faults on the NVIDIA path: The
    Ingestion Tax, for weights.
  - The gap is stated in the literature: "No hardware or OS mechanism
    enforces this; the GPU memory remains fully writable" (Bit-Flip paper,
    on vLLM prefix blocks), answered there with a checksum.
  - Access control on shared KV as an abstraction: Symphony's KVFS ("readable
    by all LIPs but writable only by the admin"). As a requirement: SGLang
    RFC #35648 ("page ownership prevents concurrent writes"), by leases.
  - The OS form: IO-Lite ("read-only sharing of immutable buffers ensures
    fault isolation, protection, and consistency"); `F_SEAL_FUTURE_WRITE`
    exists for exactly "one process ... can continue to modify while sharing
    that buffer on a "read-only" basis".
- **Exact difference.**
  - Who can lift the protection. With CUDA VMM the mapping process chooses
    its own access with `cuMemSetAccess`, and the export call has no flag to
    restrict the importer ("flags – Reserved, must be zero"). With legacy
    CUDA IPC there is no read-only import at all. A host file can be handed
    out so that the receiver cannot obtain a writable shared mapping (file
    mode, or a sealed `memfd`). This is the one real difference, and it
    rests on documentation only (Section 5, check A).
  - Which MMU. Host page tables through the SMMU, not GPU page tables set by
    the driver; therefore the same protection holds across MIG instances.
  - Scope. Across OS processes, for KV, with the effect on the other sharers
    measured per sharing mode. onnx-genai is one process; Liu et al. do not
    use the read-only mapping for sharing; The Ingestion Tax is weights and
    one statement.
- **Limits the wording must carry.** A named tmpfs file cannot be sealed
  (`fcntl(2)`: seals only on `memfd`), so in the engine path the protection
  against a process of the same user is the file mode. The publisher is
  trusted. Under MPS the faulting write ends the work of the co-clients, so
  integrity holds and availability does not. Bit flips, timing channels, and
  semantic poisoning through legitimate publication (HijackKV, provenance)
  are not addressed.

### N3. Independence from the GPU-sharing mode

**Verdict: OPEN IN THE VERIFIED SET as a measurement; the property itself
follows from vendor-documented behaviour, and one boundary (MPS client to
non-MPS process) is crossed in device memory by Liu et al.**

- **Closest work:** Liu et al. (arXiv 2605.26461v2) for sharing weights and
  KV between an MPS client and a process outside MPS; C2CServe for MIG
  instances that read host-resident weights; the CUDA Programming Guide for
  the statement that system memory mapped `MAP_SHARED` is shared "between
  different devices connected to the same host".
- **What is taken.** Fault propagation among MPS clients and its containment
  by MIG (NVIDIA, Guardian, Liu et al.; Section 14.3). One MPS server per MIG
  instance as a workflow (MIG guide). "CUDA IPC across GPU instances is not
  supported" (MIG guide). The channel between MIG instances is system memory
  (RAPIDS guide). Device-memory sharing of weights and KV across the MPS
  boundary by VMM handles (Liu et al., datacenter GPUs, active and standby).
  A shared KV pool intended to run with and without MPS on one GPU (SGLang
  RFC, proposal).
- **Exact difference.** No opened work shares LLM state between MIG
  instances without a copy, and none reports one sharing mechanism under
  time slicing, MPS, MIG, and MPS inside each MIG instance. C2CServe keeps
  weights in pinned host memory per process and the text read does not say
  that two instances map one copy. Liu et al. share between one writer and
  its idle standby, not between concurrent sharers, and not across MIG.
- **What remains claimable:** the measurement on this device, and the
  statement that the host-mapping route is the one route found that reaches
  all four placements. It is a corollary of N6's mechanism, not a second
  mechanism (same caveat as C2 in Section 16.4).
- **Open lead.** The MIG guide says that from driver R570 "P2P between MIG
  instances on the same GPU is supported". The Tegra note says "Peer to peer
  (P2P) communication calls are not supported on Tegra". Whether P2P gives a
  shared device mapping across MIG instances on datacenter GPUs was not
  found in any opened source.

### N4. CPU populate-ahead of memory that the GPU will write

**Verdict: TAKEN as a technique. Only its application to a host-memory KV
tail on this platform is not found.**

- **Closest work:** vAttention for the KV-specific part (allocate ahead in a
  background thread because growth is predictable); Schieffer et al. and
  Wahlgren et al. for the unified-memory part (CPU pre-population removes
  GPU first-touch faults; "use CPU prefaulting to transform them into GPU
  minor faults in advance").
- **Also taken.** Application-driven prefetch with write permission ahead of
  device IO: `IBV_ADVISE_MR_ADVICE_PREFETCH_WRITE` (2018), NPF pre-faulting
  (2017). `MADV_POPULATE_WRITE` on host KV memory so that the device path
  does not fault page by page: vLLM's KV offload region (upstream) and the
  LMCache RBLN pull request ("populate, don't register").
  `cudaMemPrefetchAsync` "to ensure that these pages get populated and avoid
  faults" (Tegra note).
- **Exact difference.** The opened uses populate a whole region once (HPC
  buffers, offload pools), or back device memory through `cuMemMap`
  (vAttention). None populates a moving window just ahead of the decode
  position in a live KV tensor that the GPU writes in place through host
  page tables, and none states the reason given here (filling an empty page
  needs no invalidation of a GPU-visible translation, a GPU write fault
  does).
- **Recommendation:** do not list N4 as a contribution. Present it as the
  known remedy applied to the tail, cite the works above, and keep the
  measured numbers as evidence for the design rule of N6.

### N5. Reclaim of shared GPU-visible state by mapping lifetime

**Verdict: PARTIALLY TAKEN.**

- **Closest work:** PyTorch's `file_descriptor` sharing strategy (the default
  for CPU tensors) for the mechanism and its trade-off; CUDA VMM handles as
  used by Liu et al. for the device-memory counterpart.
- **What is taken.** Lifetime by kernel reference with no owner process is
  the ordinary behaviour of unlinked files (a POSIX property; no source was
  opened for it in this pass). PyTorch documents sharing by passed
  descriptors as its default strategy for CPU tensors, and documents the
  alternative (named files) with its leak and the reaper daemon it needs. For device memory, a VMM allocation lives until the last handle is
  closed, and Liu et al. rely on that so that the standby keeps the state
  after the active process exits. In one process: vLLM (reference count
  zero), onnx-genai ("alive until the last sharer releases"), IO-Lite.
- **Contrast available.** Every cross-process KV store opened has an owner
  of lifetime: Plasma's store process, LMCache's MP server and the
  "child process that owns allocation and object-lifetime metadata" of RFC
  #4307, Omni-Flow's manager with reference sets and Redis, the helper
  process of SGLang RFC #35648, TraCT's shared metadata with locks. LMCache
  #5507 reports a store that never evicts. Legacy CUDA IPC and PyTorch's
  CUDA tensors need the producer alive. llama.cpp PR #21792 keeps a named
  file on purpose.
- **Exact difference.** No opened work binds the lifetime of a shared KV
  segment that GPUs read in place to the mappings of the processes that use
  it, across processes and MIG instances, with nothing else running.
- **Limit the wording must carry.** An unlinked file cannot be attached by
  name. Either the descriptor is passed (inheritance at spawn, a Unix
  socket, `/proc/<pid>/fd`), which is a rendezvous channel even if it is not
  a coordinator of lifetime, or the name stays until the last attacher has
  attached, and then a publisher that dies before the unlink leaves the
  pages allocated on a device without swap. PyTorch's documentation states
  exactly this trade-off.

### N6. The framing (operations on host mappings; no GPU-visible page changes owner through a fault)

**Verdict: PARTIALLY TAKEN.**

- **Closest work:** the CUDA Programming Guide section "Inter-Process
  Communication (IPC) with Unified Memory" for "sharing reduces to host
  mappings"; IO-Lite for the rule; Symphony for KV state as forkable,
  shareable, access-controlled files.
- **What is taken.**
  - That on a GPU with full unified-memory support, system memory is shared
    between processes by `MAP_SHARED`, POSIX shm, or `memfd`, and that the GPU
    uses page-table entries the CPU created: vendor documentation.
  - That shared state should be immutable and mapped read-only, that changes
    go to newly allocated private buffers, that composition is a list of
    ranges, and that copy-on-write is to be avoided because writes defeat it:
    IO-Lite (1999), fbufs (1993), Plasma (2017) for objects.
  - That KV state can be presented as files with open, fork, close, remove,
    sharing across processes, and access control: Symphony (2025), Pie.
  - Weights read in place from shared host mappings: The Ingestion Tax and
    the items of Section 14.
  - Host MM as owner of device-visible memory in general: GMEM and HMM
    (Section 1 of the main audit).
- **Exact difference.** No opened paper, issue, or vendor page states the
  rule for a GPU that follows host page tables, gives the platform reasons
  for it (a GPU fault in a writable mapping is served as a write to the
  whole 2 MiB block; each change of a page's owner costs a process-wide
  invalidation; the next GPU write after `fork` pays for every page), or
  derives share, fork, and move of LLM serving state from it. The vendor
  guide stops at "IPC capable" and warns of "significant performance
  implications" without saying which. Symphony's files are objects of a
  serving system over device memory. The unified-memory LLM works opened
  (EdgeAgent, Capsules, Echo, OxyGen, SiliconBench, BOOST, DAK, SuperInfer)
  are single-process or copy-based.
- **What remains claimable:** the rule as a platform-specific instance of a
  known OS principle, justified by measurements that were not found
  elsewhere (Section 16.4, C3), and applied to KV state in a real engine.
  Not claimable: the principle, the file abstraction for KV, or the fact
  that host shared mappings are visible to the GPU.

### 3.7 Works that force a change in positioning

1. **Liu et al. v2 (2 Oct 2026).** Device memory is shared, without a copy,
   for weights and KV, between an MPS client and a process outside MPS, and
   it survives the exporter. The record's sentences "an IPC handle is
   exported by a process that must stay alive" and any sentence implying
   that only the host route crosses the MPS boundary are true for legacy
   CUDA IPC and false for VMM handles. The comparison must name which
   device-memory interface is meant.
2. **CUDA 12.0 read-only `cuMemSetAccess`, and onnx-genai #777.** "Device
   memory that the importer can write" is not a property of device memory.
   N2 must be narrowed to: across processes, not liftable by the sharer, on
   host page tables, across MIG instances.
3. **Symphony (HotOS '25).** The picture "KV state is a file; processes
   open, fork, and close it; the prefix is readable by all and writable by
   one" is theirs. The paper should say that on a host-page-table GPU this
   abstraction is implemented by the operating system's own files and MMU
   instead of a file system inside the serving system.
4. **CUDA Programming Guide, IPC with Unified Memory.** The enabling
   property is documented by the vendor for systems with full unified-memory
   support. It must be cited next to the Tegra note.
5. **IO-Lite and fbufs.** The design rule must be introduced as an
   application of immutable shared buffers, with the GPU-specific reasons as
   the addition.
6. **N4 is not a contribution** (vAttention, Schieffer et al., Wahlgren et
   al., RDMA prefetch, `MADV_POPULATE_WRITE` in vLLM and LMCache).
7. **OxyGen** shares KV inside one process on Jetson AGX Thor and uses
   separate MPS processes as the baseline. It joins Execution-State Capsules
   as the work a reviewer will name for "why separate processes on Thor".

## 5. Strongest reviewer objections with honest answers

**Objection 1: "N1 to N5 are the SGLang radix tree, `mprotect`, a corollary,
`MADV_POPULATE_WRITE`, and `unlink`. Where is the idea?"**
Largely correct. Each of the five is a known mechanism, and three of them
(N2, N4, N5) are single system calls. The honest position is the one already
taken in Section 16.5: the contribution is that on this class of GPU the
whole life cycle of shared model state needs no mechanism beyond the host
memory manager, plus the measurements that say which host operations are
safe. N1 to N5 should be presented as consequences of one rule, in one
design section, and not as five contributions.

**Objection 2: "Device memory can do all of this with CUDA VMM: read-only
mappings since CUDA 12.0, lifetime by handle, sharing across the MPS
boundary (Liu et al.), page-level prefix sharing with write protection
(onnx-genai). Your own baseline shows it generates slightly faster."**
Correct inside one MIG instance, and the paper must say so. What the opened
sources leave to the host route: (a) reach across MIG instances, where the
VMM import was refused on this device and CUDA IPC is documented as
unsupported; (b) a read-only right that the sharer cannot upgrade, which
the VMM documentation does not offer (check A below); (c) no interposer on
allocation and no handle-passing protocol; (d) pageable memory backed on
demand. The argument must not rest on "device memory cannot be protected"
or "the exporter must stay alive".

**Objection 3: "Write protection against whom? The cache file is a named
tmpfs file; any process of the same user can open it for writing. And MIG
exists to separate tenants."**
For the engine path the protection is against a faulty sharer (a stray GPU
write, an engine bug, a wrong row index), not against an adversary. An
adversarial claim needs the sealed `memfd` route, which the record measured
with a synthetic kernel only. The publisher is trusted in both cases. The
RAPIDS guide presents the memory separation of MIG as a security property,
so sharing across instances must be scoped to one tenant, as Section 17
item 7 already does.

**Objection 4: "Under MPS your write fault kills every co-client. That is
worse than the checksum of the Bit-Flip paper, which keeps serving."**
Correct for availability. The protection converts silent corruption into a
fault; whether the fault is contained depends on the sharing mode (measured:
0 of 18 MPS co-clients survive, 36 of 36 others do). Liu et al. show a
driver change that contains this class of fault under MPS on datacenter
GPUs; it is not in the Thor driver that was measured. The paper should say
that page protection addresses software writes and that a checksum
addresses bit flips, and that the two compose.

**Objection 5: "The independence from the sharing mode is trivial: host
memory is host memory. NVIDIA's guide already says shared system memory
works across devices."**
Correct as a property. The claim that survives is empirical: it was run in
an engine under the four modes, with identical text and with the memory and
fault results reported, on a platform the guide does not name. It should be
one paragraph and one table, not a contribution bullet.

**Objection 6: "Populate-ahead is the standard advice for system-allocated
memory. vAttention already allocates ahead for KV."**
Correct. See N4. The paper cites them and reports the number.

**Objection 7: "'No coordinator' is not true: somebody has to tell the child
which segments to map, and in which order."**
Correct in part. The metadata sidecar and the descriptor (or name) must
reach the attacher. What is absent is a process that owns allocation and
lifetime while sharers run. The wording must separate "rendezvous at attach
time" from "ownership of lifetime", and state what happens when a publisher
dies before unlinking a named file.

**Objection 8: "The design rule is IO-Lite. The file abstraction is
Symphony."**
Correct, and both must be cited where the rule is introduced. The addition
is the device: IO-Lite's consumers were CPU protection domains, where a
copy-on-write fault costs a fault. Here the consumer is a GPU bound by
shared virtual addressing, where the measured costs are a 512-fold
amplification of a read and a process-wide invalidation per page. Symphony's
files live in a serving system; here they are the kernel's.

**Objection 9: "OxyGen and Capsules run on the same Jetson AGX Thor inside
one process. Why separate processes at all?"**
Section 17 item 10 already concedes that one batching process is faster and
smaller. The answer remains: agents that are separate programs, fault
domains, and the second MIG instance.

**Checks to run on the device before the wording of Section 4 is used.**

- **A (decides N2).** In the VMM probe, let the importer of a handle that the
  design intends as read-only call `cuMemSetAccess` with
  `CU_MEM_ACCESS_FLAGS_PROT_READWRITE` and write. The documentation implies
  that this succeeds. If it does, the sentence "the access right is chosen
  by the mapping process" is measured. If it fails, N2 loses its main
  difference inside one MIG instance.
- **B (decides the "compromised" wording).** Let an attacher of the engine
  path reopen the cache file for writing under the same user and under
  another user with mode 0444. Repeat with a `memfd` sealed with
  `F_SEAL_FUTURE_WRITE` before the publisher's last write and `F_SEAL_WRITE`
  after it.
- **C (decides N5 wording).** Kill a publisher before and after the unlink,
  and kill the last attacher, and report the tmpfs usage after each.
