# STATOR: 통합 메모리 엣지 장치의 다중 프로세스 LLM 서빙을 위한 불변 상태 익스텐트

*STATOR: Immutable State Extents for Multi-Process LLM Serving on Unified-Memory Edge Devices*

Jetson AGX Thor에서 같은 LLM을 서빙하는 여러 프로세스가 모델 가중치와 공통
프롬프트 프리픽스의 KV 캐시를 물리 메모리 한 벌로 공유한다. GPU는 두 상태를
호스트 페이지 테이블을 통해 제자리에서 읽는다.

STATOR는 전동기에서 회전하지 않는 부분의 이름이다. 공유 상태는 불변으로 고정하고
각 프로세스가 쓰는 부분만 따로 둔다는 설계 규칙에서 이름을 가져왔다. 저장소
이름과 일부 스크립트, 기록 파일 이름에 남아 있는 LLM-Share는 이전 작업명이다.

- 연구 기록: [docs/RESEARCH_LLM_SHARE_2026-10-05.md](docs/RESEARCH_LLM_SHARE_2026-10-05.md) (KV 캐시는 6절)
- 기반 측정 기록: [docs/RESEARCH_HOSTMM_2026-10-05.md](docs/RESEARCH_HOSTMM_2026-10-05.md) (코드와 원시 결과는 `thor_hostmm` 프로젝트에 있으며 이 저장소에 포함되지 않는다)
- 선행 연구 조사: [docs/SOTA_HOSTMM_2026-10-05.md](docs/SOTA_HOSTMM_2026-10-05.md) 12, 14, 16, 17절, [docs/SOTA_AUDIT6_2026-10-06.md](docs/SOTA_AUDIT6_2026-10-06.md)
- 논문 원고: 별도 저장소에서 관리한다. 논문에 쓰는 그림은 `figures/make_paper_figures.py`로 만들고 `figures/sync_to_paper.sh`로 그 저장소의 `Figures/`에 복사한다.

## 1. 서론

### 1.1 연구의 필요성

온디바이스 어시스턴트는 단일 모델 호출에서 다중 에이전트 구성으로 바뀌고
있다. 여러 프로세스가 같은 기반 모델을 사용하고, 시스템 프롬프트, 도구 설명,
참조 문서로 이루어진 같은 긴 프리픽스에서 출발한다.

통합 메모리 장치에서는 CPU와 GPU가 하나의 DRAM을 나누어 쓴다. 프로세스마다
중복해서 보유하는 상태는 그만큼 장치 전체의 메모리를 줄인다. 서빙 프로세스가
보유하는 상태는 두 가지이다.

- **가중치.** 7B 모델(Q4_K_M)은 4.4 GiB이다. 현재 엔진은 프로세스마다 가중치를
  디바이스 메모리에 복사한다. 프로세스 8개는 40.8 GiB를 차지한다.
- **KV 캐시.** 이 모델은 토큰당 56 KiB를 쓴다. 16,321토큰 프리픽스의 캐시는
  0.9 GiB이고, 32,768토큰 컨텍스트 전체는 1.75 GiB이다. 가중치를 공유한
  뒤에도 같은 프리픽스에서 출발한 에이전트 8개는 19.9 GiB를 차지한다. 이
  가운데 프리픽스 부분은 모든 에이전트에서 내용이 같다.

에이전트를 한 프로세스에 모으면 엔진이 프리픽스를 시퀀스 사이에서 공유한다.
그러나 에이전트가 서로 다른 프로그램이거나, 한 에이전트의 GPU 장애가 다른
에이전트로 전파되지 않아야 하거나, GPU의 두 MIG 인스턴스를 모두 사용해야 하는
경우에는 프로세스가 분리된다. 이 연구는 분리된 프로세스가 중복 없이 상태를
공유하는 방법을 다룬다.

### 1.2 기존 방법의 한계

프로세스 사이에서 상태를 공유하는 기존 수단은 이 장치에서 각각 한계가 있다.
근거는 2.3절에 있다.

- 엔진이 제공하는 상태 파일은 프리픽스를 프로세스마다 복사한다.
- 프로세스 내부의 프리픽스 공유는 프로세스 경계를 넘지 못한다.
- GPU 수준의 메모리 공유(CUDA IPC, CUDA 가상 메모리 인터페이스)는 MIG 인스턴스
  경계에서 거부된다.
- 커널의 copy-on-write는 GPU가 접근하는 메모리에서 정상적으로 동작하지 않는다.
  GPU의 읽기가 복사를 일으키고, 페이지 소유권이 바뀔 때마다 프로세스 전체의
  무효화 비용이 든다.

### 1.3 접근

Thor의 GPU는 호스트 페이지 테이블을 따라간다. 따라서 호스트 메모리 관리자가
GPU가 접근하는 메모리를 프로세스 사이에서, 그리고 MIG 인스턴스 사이에서 공유할
수 있다. STATOR는 copy-on-write를 쓰지 않는 다음 규칙을 세우고 llama.cpp에 두
가지로 구현한다.

> 공유 상태는 불변이며 읽기 전용으로 매핑한다. 프로세스가 쓰는 내용은 처음부터
> 그 프로세스의 사설 메모리에 둔다. 공유, 포크, 이동은 매핑에 대한 범위
> 연산으로 수행하며, GPU가 접근하는 페이지의 소유권이 폴트를 통해 바뀌지
> 않는다.

- **가중치 in-place.** 매핑한 모델 파일을 모든 프로세스의 가중치 버퍼로
  사용한다(`inplace_weights.patch`, 59줄).
- **KV 캐시 익스텐트.** 프리픽스를 계산한 프로세스가 그 행을 게시(publish)하고,
  다른 프로세스는 그 행을 읽기 전용으로 매핑한 뒤 자신이 쓰는 행을 사설
  테일(tail)에 둔다. 테일의 메모리는 사용하는 만큼만 할당된다
  (`kv_extents.patch`, 약 430줄 추가).

### 1.5 기여와 적용 범위

기여는 다음과 같다.

1. GPU가 호스트 페이지 테이블을 따라가는 장치에서 copy-on-write가 부적합한
   원인 세 가지를 측정하였다(2.3절).
2. 그 측정에서 도출한 설계 규칙과, 이를 KV 캐시에 적용한 익스텐트 메커니즘을
   제시하였다(3절).
3. 실제 엔진에 구현하고 기존 엔진의 복사, 커널 copy-on-write, 프로세스 내부
   공유, 디바이스 메모리 공유의 네 가지 기준선과 비교하였다(4절).
4. 모든 결과를 원시 로그에서 다시 계산하는 검증기와 함께 공개한다(6절).

적용 범위는 다음과 같이 제한된다. 에이전트를 한 프로세스에 둘 수 있으면
프로세스 내부 공유가 더 낫다(에이전트 8개에 대해 2.5 GiB에서 75.6 tokens/s,
익스텐트를 쓰는 프로세스 8개는 5.7 GiB에서 34 tokens/s). 익스텐트는 그 공유를
프로세스 경계와 MIG 경계 너머로 잇는 수단이다. 측정한 구성 가운데 가장 좋은
것은 MIG 인스턴스마다 배칭 서버를 하나씩 두고 게시된 프리픽스 하나를 공유하는
구성이며, 2.4 GiB에서 102.9 tokens/s를 낸다. 메커니즘을 이루는 요소는 각각
선행 연구가 있으며(2.4절), 호스트 페이지 테이블을 통한 조합은 조사한 범위에서
찾지 못하였다. 측정은 장치 한 대, 엔진 하나, 모델 하나에서 이루어졌다.

## 2. 배경

이 절은 설계를 이해하는 데 필요한 네 가지를 다룬다.

1. 대상 플랫폼에서 GPU가 호스트 메모리에 접근하는 방식(2.1절)
2. 서빙 프로세스가 보유하는 상태와 현재 엔진이 그 상태를 다루는 방식(2.2절)
3. 그 상태를 프로세스 사이에서 공유하는 기존 수단이 이 플랫폼에서 성립하지
   않는 이유(2.3절)
4. 가장 가까운 선행 연구가 다루는 범위(2.4절)

2.5절은 이 네 가지에서 도출되는 설계 요구사항을 정리한다.

### 2.1 플랫폼: 호스트 페이지 테이블을 따라가는 GPU

대상은 NVIDIA Jetson AGX Thor이다(커널 6.8.12-1021-tegra, 오픈 GPU 커널 모듈
595.78, `uvm_ats_mode=1`, CUDA 13.0). GPU는 ARM SMMUv3의 공유 가상 주소 지정을
통해 프로세스의 주소 공간에 연결된다. CUDA 커널은 페이지 가능한 일반 호스트
메모리를 복사 없이 제자리에서 읽고 쓴다. GPU는 자체 메모리가 없는 두 개의 MIG
인스턴스, `2g.0gb`(12 SM)와 `1g.0gb`(6 SM)로 나뉘어 있다.

12 SM과 6 SM으로 나눈 것은 이 연구의 선택이 아니라 이 장치가 제공하는 유일한 다중
인스턴스 배치이다. 장치의 MIG 프로파일은 GPU의 20 SM을 세 슬라이스로 나누며, 한
슬라이스 프로파일(6 SM)은 세 번째 슬라이스에만, 두 슬라이스 프로파일(12 SM)은 앞의
두 슬라이스에만 놓을 수 있고, 프로파일마다 인스턴스는 하나이다(`nvidia-smi mig -lgip`,
`-lgipp`). 따라서 9/9나 6/6/6 분할은 없다. 또한 모든 프로파일의 메모리가 0 GiB이므로
MIG는 연산만 나누고 메모리는 나누지 않는다. 모든 인스턴스가 하나의 메모리 풀을 쓰기
때문에 인스턴스 사이의 중복이 그대로 비용이 되고, 호스트 매핑으로 인스턴스 사이의
공유가 가능하다. 평가는 결과를 인스턴스별로 보고한다.

이 구조에서 GPU가 접근하는 메모리의 매핑, 보호, 공유는 호스트 메모리 관리자가
결정한다. 프로세스 사이의 공유도 호스트 페이지 테이블 수준에서 이루어지므로
MIG 인스턴스 경계의 영향을 받지 않는다.

### 2.2 서빙 프로세스의 상태와 현재 엔진의 처리

서빙 프로세스는 가중치와 KV 캐시를 보유한다.

- **가중치**는 실행 중에 바뀌지 않는다. llama.cpp는 통합 GPU에서 메모리 매핑을
  끄고 가중치를 디바이스 메모리에 복사한다. CUDA 백엔드는 호스트 매핑을
  버퍼로 받지 못한다.
- **KV 캐시**는 실행 중에 계산된다. 캐시의 셀은 해당 토큰이 디코딩될 때 한 번
  기록되고, 한 시퀀스의 셀은 순서대로 채워진다. 엔진은 컨텍스트를 만들 때
  컨텍스트 전체 크기의 캐시를 할당하고 0으로 채운다.
- **프리픽스의 전달.** 프리픽스의 캐시는 행 전체를 담은 상태 파일을 통해 다른
  프로세스로 전달되며, 받는 프로세스는 그 행을 자신의 캐시에 복사한다.

### 2.3 기존 공유 수단의 한계

**커널의 copy-on-write.** 다른 프로세스의 메모리를 사설로 볼 수 있게 하는
커널의 기본 수단은 쓰기 가능한 사설 매핑(`MAP_PRIVATE`)과 `fork`이다. 두 수단은
모두 copy-on-write에 의존한다. 이 장치에서 측정한 세 가지 성질 때문에
copy-on-write는 GPU가 접근하는 메모리에 적합하지 않다
(`docs/RESEARCH_HOSTMM_2026-10-05.md`).

|---|---|
| GPU는 accessed 플래그가 지워진 페이지에서 폴트를 내고, 드라이버는 쓰기 가능한 매핑의 폴트를 주변 2 MiB 블록 전체에 대한 쓰기로 처리한다 | 해당 페이지 1개가 512개 페이지를 사설 복사본으로 만든다. 블록마다 1개씩 있으면 객체 전체가 복사된다 |
| GPU를 사용하는 프로세스에서 단일 페이지 플러시는 주소 공간의 어느 위치에서든 약 9 us가 든다. 범위 연산에는 추가 비용이 없다 | copy-on-write 해제, 재사용 폴트, 페이지 단위 `mprotect`와 `MADV_DONTNEED`가 4.3~9.0배 느려진다 |
| `fork` 이후 fork 이전 메모리에 대한 다음 GPU 쓰기는 모든 페이지의 비용을 치른다 | GiB당 2.7초. `posix_spawn`이나 `MADV_DONTFORK`로 피할 수 있다 |

**GPU 수준의 공유.** CUDA IPC와 CUDA 가상 메모리 인터페이스는 한 MIG 인스턴스
안에서는 디바이스 메모리를 공유하지만 인스턴스 사이에서는 거부된다.

**MPS.** MPS 클라이언트 하나의 GPU 폴트는 같은 서버의 모든 클라이언트를
종료시킨다(18개 가운데 0개 생존). 시분할 프로세스와 다른 MIG 인스턴스의
프로세스는 영향을 받지 않는다(36개 가운데 36개 생존).

**프로세스 내부의 공유.** vLLM, SGLang, llama.cpp의 슬롯은 한 프로세스의 요청
사이에서 프리픽스를 공유한다. 이 공유는 프로세스 경계에서 끝난다.

### 2.5 설계 요구사항

위 내용에서 다음 요구사항이 도출된다.

| 요구사항 | 근거 |
|---|---|
| 공유 상태는 읽기 전용으로 매핑한다 | 쓰기 가능한 매핑에서는 GPU 읽기가 복사를 일으킨다(2.3절) |
| 프로세스가 쓰는 내용은 처음부터 사설 메모리에 둔다 | 페이지 소유권이 바뀔 때마다 무효화 비용이 든다(2.3절) |
| 공유, 포크, 이동은 범위 연산으로 수행한다 | 범위 연산에는 추가 비용이 없다(2.3절) |
| 프로세스는 `fork`가 아니라 새로 실행한다 | `fork`는 이후의 GPU 쓰기에 비용을 남긴다(2.3절) |
| 공유 경로는 호스트 페이지 테이블이어야 한다 | GPU 수준 공유는 MIG 경계에서 거부되고, MPS는 장애를 전파한다(2.3절) |

## 3. 설계

### 3.1 설계 규칙과 전체 구조

설계 규칙은 2.5절의 요구사항을 하나로 묶은 것이다.

> 공유 상태는 불변이며 읽기 전용으로 매핑한다. 프로세스가 쓰는 내용은 처음부터
> 그 프로세스의 사설 메모리에 둔다. 공유, 포크, 이동은 매핑에 대한 범위
> 연산으로 수행하며, GPU가 접근하는 페이지의 소유권이 폴트를 통해 바뀌지
> 않는다.

<p align="center"><b>그림 2.</b> 전체 구조. 각 프로세스는 모델 파일과 게시된 프리픽스의 행을 읽기 전용으로 매핑하고, 자신이 쓰는 행을 사설 테일에 둔다. 두 MIG 인스턴스의 GPU는 호스트 페이지 테이블을 통해 이 메모리를 제자리에서 읽는다. (1) 게시, (2) 연결, (3) 테일 확장.</p>

그림 2는 세 층으로 구성된다. 위층은 두 MIG 인스턴스로 나뉜 GPU이다. 가운데
층은 서빙 프로세스의 주소 공간이며, 각 주소 공간은 가중치, 프리픽스의 행,
테일의 행으로 이루어진다. 아래층은 호스트 물리 메모리이다. 가중치 영역과

가리킨다. 테일 영역의 매핑은 쓰기 가능하며 프로세스마다 다른 페이지를
가리킨다. 프로세스 사이의 공유가 호스트 페이지 테이블에서 이루어지므로 두
MIG 인스턴스의 프로세스가 같은 페이지를 공유한다.

### 3.2 가중치 in-place

CUDA 백엔드가 호스트 매핑을 버퍼로 받도록 한다(`GGML_CUDA_HOST_PTR=1`). 엔진은
모델 파일을 공유 읽기 전용으로 매핑하여 가중치 버퍼로 사용한다. 읽기 전용
매핑은 GPU 읽기에 의해 사설 복사본으로 바뀌지 않는다. GPU는 accessed 플래그를
설정하지 못하므로, 로드할 때 CPU가 파일 전체를 한 번 읽어 플래그를 설정한다.
이 과정이 없으면 첫 커널이 모든 페이지에서 폴트를 낸다. 모델을 2 MiB 페이지
(`huge=always`로 마운트한 tmpfs 또는 hugetlbfs)에 두면 작은 페이지의 비용이
없어진다. 행 길이가 512의 배수가 아닌 양자화 텐서는 거부한다. 읽기 전용
매핑에는 행 패딩을 둘 공간이 없기 때문이다.

### 3.3 KV 캐시 익스텐트

캐시의 셀은 한 번 기록되고 순서대로 채워진다(2.2절). flash attention과 단일
스트림을 사용할 때 셀은 모든 키 텐서와 값 텐서의 한 행이다. 따라서 공통
프리픽스의 셀은 모든 텐서의 앞부분 범위가 되고, 에이전트가 추가하는 내용은 그
뒤에 놓인다(그림 3).

<p align="center"><img src="figures/design_layout.png" width="760"></p>
<p align="center"><b>그림 3.</b> 캐시의 키 또는 값 텐서 하나를 익스텐트로 구성한 모습. 프리픽스의 행은 게시자의 파일에서 읽기 전용으로 매핑되어 모든 에이전트에서 같은 물리 페이지이다. 에이전트가 쓰는 행은 CPU가 GPU보다 앞서 채워 두는 사설 메모리에 놓인다.</p>

- **게시(publish).** 게시자의 캐시는 tmpfs의 파일이다. 컨텍스트의 상태를
  저장하면 셀의 메타데이터(셀당 16바이트)만 기록되고 행은 기록되지 않는다.
  사용 중인 행은 텐서마다 `mprotect` 한 번으로 게시자 자신에게도 읽기 전용이
  되고, 해당 셀은 동결된다.
- **연결(attach).** 에이전트는 프리픽스 행의 온전한 페이지를 파일에서 사설
  읽기 전용으로 각 텐서의 시작 위치에 매핑한다. 일부만 채워진 마지막 페이지는
  복사하고, 텐서의 나머지는 사설 메모리로 둔다. CPU가 매핑한 페이지를 한 번
  읽어 accessed 플래그를 설정한다. 상태 파일을 읽으면 메타데이터가 복원되며
  행은 읽지 않는다.
- **동결 셀.** 캐시는 동결된 셀을 다시 내주지 않는다. 에이전트가 프리픽스의
  토큰을 버리거나 다시 쓰면 새 셀은 자신의 테일에 놓인다. 매핑이 읽기
  전용이므로 이를 통한 쓰기는 시도한 프로세스의 폴트가 된다.
- **사용량을 따라가는 테일.** 사설 영역은 메모리 없이 시작한다. 디바이스가
  배치의 셀을 쓰기 전에 CPU가 해당 행의 페이지를 256행 앞서 채운다. 비어 있는
  페이지를 채우는 데에는 무효화가 필요하지 않다.
- **포크(fork).** 상태를 저장한 게시자는 계속 실행된다. 게시자의 다음 셀은
  동결된 셀 뒤에 놓인다. 자식은 에이전트로 연결한다.
- **이동(move).** 게시하고, 다른 프로세스에서 연결한 뒤, 게시자를 종료한다.
  파일은 그것을 채운 프로세스가 종료된 뒤에도 유지된다.

이 동작은 모두 호스트 매핑이므로 두 MIG 인스턴스 사이에서도 성립한다.

<p align="center"><img src="figures/design_lifecycle.png" width="720"></p>
<p align="center"><b>그림 4.</b> 매핑에 대한 연산으로서의 게시와 연결. 포크는 게시자가 계속 실행되는 경우이고, 이동은 게시자가 종료되는 경우이다.</p>

### 3.4 익스텐트 체인

에이전트는 트리를 이룬다. 루트가 공통 프리픽스를 계산하고, 그룹 리더가 그룹의
문맥을 덧붙이며, 리프가 각자의 작업을 덧붙인다. 한 단계의 익스텐트에서는
프리픽스에 연결한 리더가 자신이 덧붙인 행을 넘기지 못하므로, 리프는 공통
프리픽스만 공유하고 그룹 문맥을 다시 계산해야 한다. 익스텐트 체인은 배치를 두
개의 익스텐트에서 조상마다 세그먼트 하나를 두는 사슬로 확장한다(그림 5).

- **덧붙인 행의 게시.** 게시하려는 에이전트는 사설 익스텐트를 익명 메모리가
  아닌 자신의 세그먼트 파일에 둔다. 게시할 때 덧붙인 행을 동결하고 메타데이터만
  담은 상태 파일을 쓴다.
- **사슬에 연결.** 후손은 파일 목록과 각 세그먼트가 끝나는 행을 받는다. 텐서마다
  각 세그먼트의 온전한 페이지를 해당 파일에서 읽기 전용으로 매핑하고, 두
  세그먼트가 만나는 페이지는 복사한다.
- **세그먼트의 수명.** 세그먼트의 페이지는 파일에 속하고 커널이 매핑 수를 센다.
  공유하는 프로세스가 모두 연결한 뒤에는 파일 이름을 지워도 되며, 마지막
  프로세스가 매핑을 해제하거나 종료할 때 메모리가 반환된다. 공유자를 추적하는
  별도 프로세스는 없다.

<p align="center"><b>그림 5.</b> 에이전트 트리와 리프 텐서 하나의 익스텐트 체인. (1) 루트가 공통 프리픽스를 게시한다. (2) 리더가 덧붙인 행을 게시한다. (3) 리프가 두 세그먼트에 연결한다.</p>

## 4. 평가

모델은 Qwen2.5-7B-Instruct Q4_K_M(4.36 GiB)이다. 셀마다 6회 반복하였고, 실행
순서를 번갈아 바꾸었으며, 두 인스턴스가 관여하는 실험에서는 역할을 번갈아
바꾸었다. 비율은 같은 반복 안에서 짝지어 계산하고 95% 신뢰구간을 붙였다.
통과 기준은 캠페인을 실행하기 전에 러너에 기록하였고, 러너는 해시로 고정된다.
`verify_llm_share_artifact.sh`는 GPU 없이 모든 요약을 원시 로그에서 다시
계산하고 아래의 관계를 다시 평가한다.

에이전트 8개가 게시자 캐시 파일의 쓰기 가능한 사설 매핑을 통해 16,321토큰

### 4.4 실행 중인 부모의 포크 (기록 6.5절)

부모가 4,081토큰 프리픽스를 자식 4개에 넘기고, 자식이 생성하는 동안 자신도

텍스트를 생성한다. 모든 자식은 복사로 상태를 받은 자식과 같은 텍스트를
생성한다(24개 가운데 24개). 자식들의 메모리는 4.4 GiB에서 2.8 GiB로 줄어든다.

### 4.8 격리와 배치 (기록 4, 5절)

- MPS 클라이언트 하나의 GPU 폴트는 같은 서버의 다른 클라이언트를 종료시키고
  (18개 가운데 0개 생존) 그 밖의 프로세스에는 영향을 주지 않는다(36개 가운데
  36개). 메모리 공유는 MIG, 시분할, MPS에서 같다.
- 프로세스를 분리해도 처리량은 늘지 않는다. MIG 인스턴스 하나의 합계는 공유하는
  프로세스 수와 무관하게 25~29 tokens/s이다.
- 각 MIG 인스턴스는 매번 같은 캐시 비트를 계산하지만, 두 인스턴스가 같은 비트를
  계산한 경우는 없다(6회 가운데 0회). 다른 인스턴스의 프리픽스를 이어 가는
  에이전트는 그 상태를 복사한 에이전트와 같은 텍스트를 생성하며, 자신의
  인스턴스에서 다시 계산한 텍스트와는 다를 수 있다.

### 4.10 추가 캠페인 (기록 6.11~6.12절)

### 4.11 보강 캠페인 (2026-10-07, 기록 6.14절)

앞 절까지의 비교는 대부분 가중치를 양쪽 모두 in-place로 둔 상태에서 KV 캐시만
비교하였다. 이 절은 수정하지 않은 엔진 전체와의 비교, 조정한 기준선, 구성 요소별
기여, 결함 격리, 실제 파이프라인을 다룬다. 모두 셀당 6회 반복이다.

**전체 스택의 메모리와 수용 한계.** 에이전트가 무엇을 공유하는지에 따라 네 스택을
비교한다. `무수정`은 패치를 적용하지 않은 같은 커밋의 엔진으로, 에이전트마다
가중치를 디바이스 메모리에 복사하고 프리픽스를 상태 파일에서 복사한다. `KV 공유`와
`가중치 공유`는 두 메커니즘 중 하나만 적용하고, STATOR는 둘 다 적용한다. 에이전트
워크로드(프리픽스 14,282토큰, 컨텍스트 16,384)를 사용하며, 반복마다 페이지 캐시를
비우고 모델 파일을 다시 읽은 뒤 측정한다.

| 스택 | 에이전트 1개당 증가 (GiB) | 에이전트 8개 (GiB, 공유 파일 포함) | 가용 메모리 117.2 GiB에 들어가는 에이전트 수 (직선 외삽) | 측정한 최대 개수 |
|---|---:|---:|---:|---:|
| 무수정 | 5.99 | 47.8 | 19 | 12 (71.9 GiB) |
| KV 공유 | 5.11 | 41.6 | 22 | 12 |
| 가중치 공유 | 1.57 | 16.9 | 71 | 32 |
| STATOR | 0.69 | 10.8 | 163 | 128 (87.7 GiB + 파일 5.1 GiB) |

에이전트 8개의 47.8 GiB 가운데 35.2 GiB는 가중치 복사 8개이고 7.0 GiB는 KV 캐시
복사 8개이다. STATOR의 10.8 GiB는 한 번만 존재하는 모델 파일 4.4 GiB와 캐시 파일
0.8 GiB, 그리고 에이전트 고유 상태 5.6 GiB로 이루어진다. 두 메커니즘의 절감은
서로 다른 부분에서 나오며, 둘을 함께 적용한 절감은 각각의 절감을 더한 값과
0.1% 차이이다. 복사하는 스택은 장치 메모리를 소진하므로 12개를 넘겨 실행하지
않았고, 수용 한계는 측정점에 맞춘 직선을 가용 메모리까지 연장한 값이다. STATOR는
별도 캠페인(`20261007-engine-kvstack-capacity-v1`, 2회 반복)에서 96개와 128개를
실행하였다. 실패 없이 66.0 GiB와 87.7 GiB를 사용하였고 직선과의 차이는 1%
이내이며, 128개의 처리량 합은 36.3 tokens/s이다. 모든
스택과 개수에서 같은 번호의 에이전트는 같은 텍스트를 생성한다.

생성 속도는 무수정 대비 `KV 공유` 0.96~0.98, `가중치 공유` 0.93~0.97, STATOR
0.91~0.95이다. 사전 기준(모든 개수에서 0.92 이상)은 에이전트 1개인 칸(0.913)에서
충족되지 않는다. 손실은 인스턴스에 따라 다르다. 에이전트 하나가 12-SM
인스턴스에서 실행되면 4.5%를 잃고 그 전부가 4 KiB 페이지 캐시에 놓인 가중치에서
나온다. 6-SM 인스턴스에서는 12.7%를 잃으며 가중치가 7.7%, 캐시가 5.3%를 차지한다.
에이전트 8개가 함께 시작할 때 첫 토큰은 3.39 s에서 1.83 s로 앞당겨진다. 모델
적재가 2.43 s에서 1.08 s로, 프리픽스 연결이 275 ms에서 44 ms로 줄어들기 때문이다.

가중치에서 나오는 손실은 모델 파일의 페이지 크기에 따른 것이다. 모델 파일을 2 MiB
페이지를 쓰는 tmpfs(`huge=always`)에 두고 같은 캠페인을 반복하면
(`20261007-engine-kvstack-huge-v1`), 에이전트 8개의 생성 속도는 무수정 대비 `가중치
공유` 1.006(95% 신뢰구간 0.980~1.033), STATOR 0.994(0.969~1.020)이다. 메모리는
같다(에이전트 8개 5.6 GiB, 1개당 0.69 GiB). 에이전트 하나는 12-SM 인스턴스에서
1.02, 6-SM 인스턴스에서 0.90이며, 6-SM 인스턴스에 남는 손실은 호스트 페이지
테이블을 거치는 메모리의 비용이다(아래 원인 분리 참조). 첫 토큰은 3.32 s에서
1.65 s로 앞당겨진다. 따라서 권장 구성은 모델 파일을 2 MiB 페이지 위에 두는 것이다.

**모델 파일을 2 MiB 페이지에 올리기 (`weights_publish.c`, `20261007-weights-publish-v1`).**
위 권장 구성은 모델 파일이 2 MiB 페이지를 쓰는 tmpfs에 있어야 한다. `cp`로 복사하면
파일이 페이지 캐시를 거치므로 적재가 끝난 뒤에도 같은 크기의 사본이 페이지 캐시에
남는다. `weights_publish`는 원본을 O_DIRECT로 읽어 대상 파일의 공유 매핑에 직접
채운다(읽기 스레드 8개, 32 MiB 단위). 반복마다 페이지 캐시를 비우고 저장 장치에서
읽게 하였다.

| 파일 | 방법 | 시간 (s) | GiB/s | 페이지 캐시에 남는 사본 | 적재 중 MemFree 감소 |
|---|---|---:|---:|---:|---:|
| Qwen2.5-7B (4.4 GiB) | `cp` | 2.21 | 1.98 | 4.4 GiB | 8.6 GiB |
| | `dd iflag=direct` | 1.47 | 2.97 | 0 | 4.0 GiB |
| | `weights_publish` | 1.15 | 3.78 | 0 | 3.9 GiB |
| Qwen2.5-14B (8.4 GiB) | `cp` | 4.05 | 2.07 | 8.4 GiB | 15.8 GiB |
| | `dd iflag=direct` | 2.84 | 2.95 | 0 | 8.0 GiB |
| | `weights_publish` | 1.80 | 4.64 | 0 | 7.6 GiB |
| 14B 파일 4개를 이어 붙인 합성 파일 (33.5 GiB) | `cp` | 16.71 | 2.06 | 32.4 GiB | 64.0 GiB |
| | `dd iflag=direct` | 11.23 | 2.98 | 0 | 33.3 GiB |
| | `weights_publish` | 6.95 | 4.82 | 0 | 33.3 GiB |

직접 읽기는 `cp`보다 1.9~2.4배 빠르고, 적재 중 차지하는 메모리가 파일 크기의 2배에서
1배로 줄어든다. 54회 모두 대상 파일이 원본과 같다. 정상 상태의 메모리와 생성 속도는
어느 방법으로 올려도 같다.

**단계별 기여 (`20261007-engine-kvablate-v1`).** 익스텐트 방식의 단계를 하나씩 바꾸어
측정하였다. 부모 하나와 자식 8개, 16,321토큰 프리픽스, 자식의 절반은 다른 MIG
인스턴스에 있다.

늘어난다. 자식 480개는 모두 Copy와 같은 텍스트를 생성하고, 사전 기준 네 개가 모두
충족된다.

**6-SM 인스턴스에서 호스트 메모리가 느린 원인의 분리 (`MODE_SET=locality`,
`20261007-engine-kvlocal-12sm-v1`, `-6sm-v1`).** 4.5절은 캐시를 호스트 메모리에 두면
6-SM 인스턴스에서만 생성 속도가 떨어진다는 것을 측정하였으나 원인을 찾지 못하였다.
이 캠페인은 부모와 자식 4개를 한 인스턴스에 두고(프리픽스 16,321토큰, 128토큰 생성)
후보 네 가지를 분리한다. 표의 값은 캐시를 디바이스 메모리에 둔 `copy` 대비 자식들의
생성 속도 합이다(반복별로 짝지은 비, 괄호 안은 95% 신뢰구간).

| 캐시의 위치 | 12-SM 인스턴스 | 6-SM 인스턴스 |
|---|---:|---:|
| 호스트 메모리, 사설, 2 MiB 페이지 (행을 복사해 받음) | 1.014 (1.010~1.019) | 0.940 (0.939~0.941) |
| 호스트 메모리, 사설, 4 KiB 페이지 | 1.019 (1.016~1.022) | 0.943 (0.941~0.944) |
| STATOR (공유 프리픽스 + 사설 꼬리) | 0.997 (0.993~1.001) | 0.932 (0.930~0.933) |
| STATOR, 꼬리를 처음부터 2 MiB 페이지로 | 0.999 (0.994~1.004) | 0.932 (0.931~0.933) |
| STATOR, 프리픽스 파일이 4 KiB 페이지 | 1.000 (0.996~1.004) | 0.932 (0.931~0.933) |

12-SM 인스턴스에서는 어떤 형태의 호스트 메모리도 속도를 낮추지 않는다. 6-SM
인스턴스에서는 모든 형태가 속도를 낮춘다. 공유하지 않는 사설 캐시도 6.0%를 잃고,
공유는 여기에 0.9%p를 더하며, 페이지 크기는 0.3%p 이하로만 영향을 준다. 따라서 이
손실은 공유나 페이지 크기가 아니라 6-SM 인스턴스에서 호스트 메모리를 읽는 것 자체의
비용이다. 자식 288개는 모두 Copy와 같은 텍스트를 생성하고 사전 기준 두 개가 충족된다.

**흩어진 접근의 메모리 종류별 속도 (`run_tlb_probe.sh`, `20261007-tlb-probe-v1`).** 4.5절의
읽기 경로 탐침은 버퍼를 연속으로 읽으며, 두 인스턴스 모두에서 호스트 메모리가 디바이스
메모리만큼 빠르다는 것을 보였다. 이 탐침은 주소가 건너뛰는 접근을 더한다. 1 GiB
버퍼에서 연속 읽기, 흩어진 읽기, 흩어진 쓰기를 디바이스 메모리와 호스트 메모리(2 MiB
페이지, 4 KiB 페이지)에 대해 측정한다. 모든 스레드가 버퍼 전체를 동시에 사용한다.
표의 값은 같은 인스턴스의 디바이스 메모리 대비 속도이다(간격 64 KiB, 6회 반복).

| 호스트 메모리 | 접근 | 12-SM 인스턴스 | 6-SM 인스턴스 |
|---|---|---:|---:|
| 2 MiB 페이지 | 연속 읽기 | 1.21 | 0.99 |
| 2 MiB 페이지 | 흩어진 읽기 | 0.97 | 0.86 |
| 2 MiB 페이지 | 흩어진 쓰기 | 0.93 | 0.93 |
| 4 KiB 페이지 | 연속 읽기 | 0.016 | 0.032 |
| 4 KiB 페이지 | 흩어진 읽기 | 0.012 | 0.024 |
| 4 KiB 페이지 | 흩어진 쓰기 | 0.028 | 0.026 |

2 MiB 페이지에서 두 인스턴스가 갈리는 것은 흩어진 읽기뿐이다. 12-SM 인스턴스는
디바이스 메모리의 0.95~0.97, 6-SM 인스턴스는 0.82~0.86이다(간격 4 KiB와 64 KiB).
4 KiB 페이지에서는 두 인스턴스 모두 모든 접근이 디바이스 메모리의 1~3%로 떨어진다.
1 GiB를 4 KiB 페이지 262,144개로 두고 모든 스레드가 동시에 사용하는 경우이다.

엔진에서는 두 번째 현상이 나타나지 않는다. 프리픽스 파일이나 사설 캐시를 4 KiB
페이지에 두어도 2 MiB 페이지와 같은 속도로 생성한다(위 지역성 캠페인). 엔진의 커널은
캐시 전체가 아니라 한 계층의 텐서를 차례로 사용한다. 따라서 이 탐침은 두 인스턴스
사이에서 손실과 같은 방향의 차이 하나(호스트 메모리의 흩어진 읽기)를 찾았으나, 엔진에서의
손실 크기와 페이지 크기에 무관하다는 점은 설명하지 못한다. 6-SM 인스턴스가 호스트
메모리를 읽을 때 무엇이 다른지는 CUDA 인터페이스 아래에서 조사하지 않았다.

**공개 벤치마크의 도구 위에서 실행한 에이전트 파이프라인 (`run_engine_kvpipe.sh`,
`20261007-engine-kvpipe-huge-v1`).** 계획자가 프리픽스(시스템 프롬프트와 BFCL v4의 도구
스키마 90개, 11,788토큰)를 계산하여 게시하고, 리더 2개가 여기에 연결하여 자기 계획을
덧붙여 다시 게시하며, 리더마다 작업자 4개가 리더의 게시물에 연결하여 벤치마크의
요청과 도구 결과를 3턴 처리한다. 프로세스는 두 MIG 인스턴스에 번갈아 배치하고, 모델
파일은 세 스택 모두 2 MiB 페이지 tmpfs에 둔다. 실행 중 보드의 전력 레일을
`tegrastats`로 표본화하여 입력 레일(VIN)의 에너지를 구한다.

| 스택 | 메모리 (GiB, 캐시 파일 포함) | 완료 시간 (s) | 무수정 대비 | 입력 레일 에너지 (J) | 무수정 대비 | 작업자 첫 토큰 (s) | 작업자 생성 속도 합 (무수정 대비) |

상태를 넘기는 시간이 줄어 완료 시간은 무수정의 0.970이고, 에너지는 0.996으로 차이가

**공유자 하나의 결함이 다른 에이전트에 미치는 영향 (`run_engine_kvfault.sh`,
`20261007-engine-kvfault-v1`).** 게시자가 에이전트 워크로드의 프리픽스(14,282토큰)를 익스텐트로
게시하고 종료한 뒤 에이전트 8개가 이를 매핑하여 128토큰을 생성한다. 생성 시작 8초 뒤에 세
경우 중 하나가 일어난다. 아무 일도 없거나, 별도 프로세스가 프리픽스 파일을 읽기
전용으로 매핑한 뒤 GPU 커널로 그 안에 쓰거나, 에이전트 0을 강제 종료한다. 표는 에이전트
0을 제외한 7개(6회 반복 합 42개) 중 완료한 수이다.

|---|---:|---:|---:|---:|
| 시분할 (12-SM 인스턴스) | 42/42 | 42/42 | 42/42 | 6/6 |

| MIG 두 인스턴스 | 42/42 | 42/42 | 42/42 | 6/6 |
| 인스턴스마다 MPS 서버 | 42/42 | 24/42 | 30/42 | 6/6 |

공유 프리픽스에 대한 GPU 쓰기는 모든 방식에서 거부되고(쓰는 프로세스에서
`cudaErrorIllegalAddress`), 프리픽스 파일의 내용은 모든 사례 뒤에 그대로이다. 시분할과
MIG에서는 쓰기와 강제 종료 뒤에도 나머지 에이전트 42개가 모두 결함이 없는 경우와 같은
텍스트로 완료한다. 호스트 매핑으로 프리픽스를 공유해도 에이전트들이 하나의 결함
범위로 묶이지 않는다. MPS 서버 하나에서는 어느 경우에도 완료하는 에이전트가 없다. 이는
아무것도 공유하지 않는 프로세스에서도 나타나는 MPS 서버의 성질이다(4.8절). 인스턴스마다
MPS 서버를 두면 결함이 없는 쪽 인스턴스의 에이전트가 완료한다. 사전 기준 F1~F3은
충족되고, MPS에서의 수는 보고 대상이며 기준이 아니다.

**더 깊은 트리와 더 넓은 트리, 서브트리의 메모리 반환 (`run_engine_kvdeep.sh`,
`20261007-engine-kvdeep-v1`, `-wide-v1`).** 4.10절의 트리는 세 단계, 프로세스 11개이다.
여기서는 루트가 16,321토큰 프리픽스를 게시하고, 중간 에이전트가 부모의 게시물에
연결하여 자기 서브트리의 문맥을 덧붙여 다시 게시하며, 잎이 연결하여 작업을 덧붙이고
생성한다. 루트의 첫 자식 아래 에이전트는 64토큰을, 나머지는 그 세 배를 생성하여 첫
서브트리가 먼저 끝나게 한다.

같다(30.2 대 30.5 tokens/s). 체인의 파일은 모든 잎이 연결한 직후 디렉터리에서
제거된다. tmpfs가 보유한 페이지는 모든 프로세스가 실행 중일 때 2,352 MiB, 첫 서브트리가
끝난 뒤 1,680 MiB, 마지막 프로세스가 끝난 뒤 0이다. 서브트리의 구간은 그 구간을 매핑한
마지막 프로세스가 끝날 때 해제되고, 다른 서브트리가 아직 매핑하고 있는 조상의 구간은

반복에서 Copy의 에이전트들이 메모리를 최대 240초 기다려 생성 구간이 흩어졌고, 그

0.952~0.976). 에이전트 192개는 모두 Copy와 같은 텍스트를 생성한다. 첫 측정은 충족되지
않은 기준과 함께 기록에 남기고, 그림은 이 셀을 재측정에서 가져온다.

**긴 생성 (`N_GEN=2048`, `20261007-engine-kvscale-gen2k-v1`).** 앞의 캠페인은 에이전트당
64~192토큰을 생성한다. 여기서는 에이전트 2개(MIG 인스턴스마다 하나)가 4,081토큰 프리픽스
위에서 2,048토큰을 생성한다(컨텍스트 8,192). 두 에이전트는 6회 반복 모두 2,048토큰 전체에서
Copy와 같은 텍스트를 생성하고(12/12), 생성 속도 합은 Copy의 0.971(신뢰구간 0.969~0.972),
메모리는 1.90 GiB 대 2.44 GiB이다. 꼬리가 사용량에 따라 늘어나도 텍스트와 속도는 생성
길이에 걸쳐 달라지지 않는다.

**기존 가중치 공유 방식과의 비교 (`run_ext_weightshare.sh`, `20261007-ext-weightshare-v1`).**
cuda-llm-weight-share는 첫 프로세스의 가중치 할당을 CUDA IPC로 내보내고 뒤따르는
프로세스에 매핑하는 공개 라이브러리이며, 수정하지 않은 엔진에 미리 적재하여 쓴다.
마스터가 에이전트 워크로드의 프리픽스를 계산해 상태 파일로 저장하고, 에이전트 8개가
이를 복원하여 생성한다. 세 스택은 가중치만 다르다.

| 배치 | 스택 | 완료한 에이전트 | 메모리 (GiB) | 가중치 적재 (s) | 첫 토큰 (s) |
|---|---|---:|---:|---:|---:|
| 한 인스턴스 | 무수정 | 48/48 | 53.9 | 2.62 | 3.82 |
| 한 인스턴스 | 라이브러리 (CUDA IPC) | 48/48 | 21.1 | 2.02 | 3.24 |
| 한 인스턴스 | 가중치 in-place | 48/48 | 18.6 (모델 파일 4.4 포함) | 1.14 | 2.38 |
| 두 인스턴스 | 무수정 | 48/48 | 53.9 | 2.54 | 3.53 |
| 두 인스턴스 | 라이브러리 (CUDA IPC) | 24/48 | 37.4 | 2.37 | 3.21 |
| 두 인스턴스 | 가중치 in-place | 48/48 | 18.5 (모델 파일 4.4 포함) | 1.12 | 2.16 |

한 인스턴스 안에서는 라이브러리가 동작하여 메모리를 53.9 GiB에서 21.1 GiB로 줄인다.
가중치 in-place는 모델 파일을 포함해 18.6 GiB이고 적재가 더 빠르다. 에이전트의 절반을
다른 MIG 인스턴스에 두면 라이브러리에서는 그 인스턴스의 에이전트 24개가 완료하지
못한다. CUDA IPC가 인스턴스 사이를 넘지 못하기 때문이다(2.3절). in-place에서는 48개가
모두 완료한다. 완료한 에이전트는 모두 무수정과 같은 텍스트를 생성한다.

**vLLM (`run_ext_vllm.sh`, `20261007-ext-vllm-v1`).** 프로세스 하나 안에서 프리픽스를
공유하는 배포용 서빙 시스템이다. vLLM 0.20.0은 이 장치에서 기본 설정으로 시작하지
않는다. 모듈 세 개(xgrammar, compressed-tensors, triton)를 환경에 추가하고, 장치를
인덱스로 지정하고(vLLM이 `CUDA_VISIBLE_DEVICES`를 정수로 해석하므로 MIG 식별자를 쓸 수
없고, 인덱스 0이 12-SM 인스턴스이다), Triton에 CUDA 헤더 경로를 알려 주고, Inductor
컴파일을 끈(`-O0`) 뒤에 동작한다. GGUF 파일을 읽지 않으므로 같은 모델의 4비트 AWQ
가중치(5.2 GiB)를 사용한다. 에이전트 워크로드(14,282토큰 프리픽스)에서 요청 8개를
동시에 두 번 보낸다.

| 요청 | 완료 | 첫 토큰 (s) | 캐시에서 온 프롬프트 토큰 | 처리량 합 (tokens/s) | 메모리 (GiB, 가중치 포함) |
|---|---:|---:|---:|---:|---:|
| 빈 서버에 첫 요청 | 48/48 | 9.83 | 12,488 / 14,307 | 156.1 | 15.3 |
| 같은 요청 다시 | 48/48 | 0.68 | 14,298 / 14,307 | 153.6 | 15.3 |

vLLM은 동시에 도착한 요청 사이에서도 프리픽스를 한 번만 계산하고, 배칭으로 프로세스
8개(34 tokens/s)보다 4.5배 높은 처리량을 낸다. 에이전트들이 한 프로세스와 한 GPU
파티션을 공유할 수 있으면 이 방식이 낫다. 이 연구의 대상은 그렇게 할 수 없는
경우이다(4.6절). vLLM은 MIG 식별자로 장치를 고를 수 없어 이 캠페인에서는 6-SM
인스턴스에서 실행하지 못하였다. 4.12절은 이 제약을 플러그인의 시작 모듈로 해결하고
인스턴스마다 서버를 하나씩 둔다.

### 4.12 vLLM 통합 (2026-10-07, 기록 6.15절)

앞 절까지의 서버는 이 연구가 수정한 엔진의 것이다. 이 절은 같은 설계를 배포용 배칭
서버인 vLLM 0.20.0에 플러그인으로 적용한다. vLLM은 한 서버 안의 요청 사이에서만
프리픽스를 공유하므로, 서버를 MIG 인스턴스마다 하나씩 두면 가중치와 프리픽스가
서버마다 한 벌씩 존재한다.

**플러그인 (`vllm_stator/`, 파이썬 460줄).** vLLM의 파일은 수정하지 않는다. 일반
플러그인 진입점(`vllm.general_plugins`)과 KV 커넥터 인터페이스만 사용하며, 환경
변수가 설정된 경우에만 다음 세 곳을 감싼다.

- **가중치.** 첫 서버는 vLLM이 모델을 적재하고 커널 형식으로 변환하도록 둔 뒤, 64 KiB
  이상인 텐서 283개(5.19 GiB)를 2 MiB 페이지 tmpfs의 파일 하나에 기록한다. 파일을
  매핑하고 GPU가 텐서를 매핑 위로 복사하므로 게시는 0.15 s에 끝난다(`tensor.cpu()`를
  거치면 21 s). 이후 모든 서버는 이 파일의 읽기 전용 공유 매핑 위에 CUDA 텐서를
  만들어 파라미터를 교체한다. 교체 뒤 디바이스 메모리에 남는 양은 5,343 MiB에서
  17 MiB로 줄고, vLLM은 "Model loading took 0.0 GiB memory"라고 기록한다.
- **프리픽스.** vLLM에 블록 하나가 모든 계층에 걸쳐 연속인 캐시 배치를 요청한다(이
  배치에서 16토큰 블록은 917,504바이트이다). 이 배치의 할당 하나를 바꾸어, 첫 서버의
  캐시는 파일의 공유 매핑이 되고, 나중에 시작하는 서버의 캐시는 사설 익명 메모리이되
  게시된 블록의 구간만 그 파일의 읽기 전용 공유 매핑이 된다. 첫 서버의 첫 요청이
  끝나면 커넥터가 가득 찬 블록의 해시를 기록하고 그 블록을 고정하며 구간을 쓰기
  금지한다. 나중 서버는 그 해시를 자기 블록 풀에 등록하므로, vLLM의 프리픽스 캐시가
  이 블록을 찾고 다른 요청에 내주지 않는다. 커넥터는 데이터를 옮기지 않는다.
- **장치 이름.** vLLM 0.20.0은 계층 모듈을 임포트하면서 `CUDA_VISIBLE_DEVICES`를 정수로
  해석하므로 MIG 식별자를 받지 못한다(4.11절). `python -m stator_vllm.serve`는 이름을
  먼저 받아들이게 한 뒤 vLLM의 명령행을 실행한다. 아래의 모든 구성은 기준선을 포함하여
  이 모듈로 시작한다.

두 서버는 같은 `PYTHONHASHSEED`를 사용해야 한다(vLLM이 블록 해시의 시드로 쓴다).
서버는 시작할 때 연결하므로, 프리픽스는 나중 서버가 캐시를 할당하기 전에 게시되어
있어야 한다.

**캠페인 (`run_vllm_share.sh`, `20261007-vllm-share-v1`).** Qwen2.5-7B-Instruct의 4비트
AWQ 가중치, 서버당 KV 캐시 2 GiB, `-O0`을 사용한다. 서버 1이 12-SM 인스턴스에서
시작하여 에이전트 워크로드의 프리픽스(14,282토큰)만 담은 요청에 응답한 뒤, 서버 2가
6-SM 인스턴스에서 시작한다. `first` 단계는 프리픽스를 계산한 적이 없는 서버 2에
에이전트 4개를 보내고, `both` 단계는 두 서버에 다른 에이전트를 4개씩 동시에 보내며,
`alone1`과 `alone2` 단계는 각 서버에 요청 하나를 단독으로 보낸다. 구성은 여섯 가지이고
6회 반복하며, 구성의 순서는 반복마다 돌아간다.

| 구성 | 내용 |
|---|---|
| vLLM | 수정하지 않은 서버 두 개 |
| vLLM-CPU | vLLM 자체의 캐시 블록 CPU 오프로드(`--kv-offloading-backend native`, 서버당 2 GiB). 버퍼는 서버 하나에 속한다 |
| vLLM-LMCache | LMCache 0.5.5. 두 서버가 함께 쓰는 호스트 메모리 저장소 프로세스(`lm://`), 256토큰 청크, 압축 없음, 서버 자체 캐시 없음, 서버당 스테이징 풀 1 GiB |
| 가중치만, 프리픽스만 | 플러그인의 두 부분 중 하나만 적용 |
| vLLM-STATOR | 플러그인의 두 부분 모두 적용 |

LMCache의 다중 프로세스 방식은 사용하지 않았다. 그 방식의 서버는 vLLM 작업자의
캐시를 CUDA IPC로 여는데, 두 MIG 인스턴스는 서로의 핸들을 받아들이지 않는다(2.3절).

| 구성 | 두 서버의 메모리 (GiB) | 시작 구간을 포함한 최대 (GiB) | 서버 2의 첫 토큰 (s) | 처리량 합 (tokens/s) | vLLM 대비 | 12-SM, 6-SM 서버 (vLLM 대비) |
|---|---:|---:|---:|---:|---:|---:|
| vLLM | 20.71 | 21.16 | 14.13 | 145.7 | 1.000 | 1.000, 1.000 |
| vLLM-CPU | 24.82 | 24.85 | 14.16 | 146.1 | 1.003 | 0.999, 1.007 |
| vLLM-LMCache | 26.01 | 26.06 | 1.79 | 145.1 | 0.996 | 0.995, 0.998 |
| 가중치만 | 15.22 | 21.01 | 14.19 | 137.9 | 0.946 | 1.007, 0.860 |
| 프리픽스만 | 20.00 | 21.22 | 0.63 | 142.4 | 0.977 | 0.997, 0.950 |
| vLLM-STATOR | 14.46 | 20.99 | 0.65 | 138.4 | 0.950 | 1.041, 0.820 |

메모리는 서버 1을 시작하기 전부터 사례가 끝날 때까지의 `MemAvailable` 감소이며 공유
파일을 포함한다.

**메모리.** 수정하지 않은 서버 두 개는 20.71 GiB를 차지한다. vLLM의 오프로드는 서버마다
버퍼를 더하고(24.82 GiB), LMCache는 스테이징 풀과 저장소 프로세스, 그리고 저장소 안의
세 번째 프리픽스 복사본을 더한다(26.01 GiB). 플러그인을 적용하면 14.46 GiB로
6.25 GiB가 줄어든다. 서버 2가 가중치 5.19 GiB와 프리픽스 블록 0.76 GiB를 복사하지 않고
매핑하기 때문이다. 다만 시작 구간의 최대값은 줄지 않는다(20.99 GiB 대 21.16 GiB).
vLLM의 로더를 그대로 사용하므로, 시작하는 서버는 플러그인이 교체할 때까지 가중치의
디바이스 복사본을 잠시 보유한다.

**서버 2의 첫 토큰.** vLLM, vLLM-CPU, `가중치만` 구성에서는 서버 2가 프리픽스를 직접
계산한다(14.1~14.2 s). LMCache에서는 저장소에서 14,080토큰을 0.90 s 동안 복사하고
1.79 s 뒤에 응답하며, 서버 1은 이 토큰을 저장하는 데 요청 안에서 0.41 s를 썼다.
플러그인에서는 서버 2가 시작할 때 블록 892개를 23 ms에 매핑하고 0.65 s 뒤에
응답하며, 게시는 아무것도 복사하지 않는다.

**처리량.** `both` 단계의 에이전트 8개의 생성 속도 합은 플러그인에서 138.4 tokens/s,
vLLM에서 145.7 tokens/s이고, 반복별로 짝지은 비는 0.950(중앙값 0.951)이다. 손실은
6-SM 인스턴스에 있다. 6-SM 서버는 vLLM의 0.820으로 생성하고 12-SM 서버는 1.041로
생성한다. 가중치만 공유하면 6-SM 서버는 0.860, 프리픽스만 공유하면 0.950이다. 4.5절이
이 엔진에서 측정한 6-SM 인스턴스의 호스트 메모리 비용과 같은 방향이며, 여기서는
가중치도 호스트 메모리에서 읽으므로 더 크다. 인스턴스별로 공유할 상태를 고를 수 있다.

**텍스트.** 요청을 단독으로 보낸 `alone1`, `alone2`에서는 모든 구성이 두 인스턴스에서
6회 모두 vLLM과 같은 텍스트를 생성한다. `alone2`에서 플러그인과 LMCache의 프리픽스는
다른 인스턴스가 계산한 것이다. 동시 요청에서는 vLLM 자신을 제외한 모든 구성에서 몇
개가 달라지며, 아무것도 공유하지 않는 구성도 같다(72개 중 vLLM-CPU 67개, LMCache
69개, 플러그인 세 구성 66~67개가 같음). vLLM이 한 서버의 시퀀스를 배치로 묶고 그
구성이 실행마다 달라지기 때문이다. 사전 기준 V1~V6은 모두 충족된다.

**서버 네 개 (`SERVERS=4`, `20261007-vllm-share-4srv-v2`, 2회 반복).** 서버 3과 4가 두
인스턴스에 하나씩 더 시작하여 서버 2와 같은 방식으로 연결한다. `both` 단계 전에 서버
3과 4에 요청을 하나씩 보내 모든 서버가 프리픽스를 가진 상태에서 에이전트 16개가
동시에 생성하게 한다(`run_vllm_share2.sh`).

캠페인에서 충족되지 않는다(0.519). 메모리와 첫 토큰은 두 캠페인이 일치한다.

## 5. 한계

- 주 평가는 장치 한 대, 엔진 하나, 7B 모델 하나에서 수행하였고, 8B와 14B
  모델은 에이전트 8개인 경우만 반복하였다. DGX Spark, Grace Hopper, Apple
  장치에서는 측정하지 않았다.
- 캐시 실험 대부분은 작은 드라이버 프로그램(`kv_fork`, `kv_batch`,
  `kv_spawn`, `kv_tree`)으로 수행하였다. `llama-server` 경로는 슬롯 저장과
  복원으로 검증하였으며, 프리픽스를 토큰 경계에서 게시해야 복사와 같은 응답이
  나온다.
- 익스텐트 체인은 네 단계(프로세스 23개)와 잎 16개의 트리까지 측정하였다.
- 에이전트는 게시자를 신뢰한다. 캐시 파일을 쓸 수 있는 주체는 모든 에이전트의
  프리픽스를 바꿀 수 있다. 캐시를 공유하는 프로세스 사이의 타이밍 채널은 다루지
  않는다. MIG 인스턴스 사이의 공유는 한 테넌트의 에이전트를 대상으로 한다.
- 6-SM 인스턴스에서 호스트 메모리의 비용(KV 캐시 6.0~6.8%, 가중치까지 호스트
  메모리에서 읽는 vLLM 서버 18%)은 공유나 페이지 크기와 무관하다는 것까지 분리하였다.
  탐침에서는 호스트 메모리의 흩어진 읽기만 이 인스턴스에서 더 느렸고, 그 아래의
  원인은 조사하지 않았다.
- 캐시는 flash attention과 단일 스트림을 사용해야 한다. 동결된 셀은 해당
  에이전트가 다시 쓰지 못한다. 캐시 파일은 스왑이 없는 장치에서 회수되지 않는
  메모리이다.
- vLLM 플러그인은 서버가 시작할 때 프리픽스에 연결한다. 실행 중인 서버에 나중에
  게시된 프리픽스를 붙이는 경로는 구현하지 않았다. vLLM의 로더를 그대로 쓰므로
  시작하는 서버는 가중치의 디바이스 복사본을 교체 전까지 보유하고, 시작 구간의 최대
  메모리는 줄지 않는다. 6-SM 인스턴스의 서버는 가중치와 캐시를 호스트 메모리에서
  읽을 때 생성 속도의 18%를 잃는다. 동시 요청의 텍스트는 vLLM의 배치 구성에 따라
  달라지므로 단독 요청으로만 동일성을 확인하였다.
- Demand, Device 기준선은 선행 연구의 방식을 이 연구에서 같은 엔진에 구현한
  것이며 해당 연구의 코드가 아니다. Device의 연결 시간은 조정하지 않은 구현의
  값이다.

## 6. 구성물과 재현

평가 그래프는 한 가지 색 규칙을 쓴다. 회색은 상태를 복사하는 기준선(Copy, 무수정, vLLM), 청록은 STATOR이고, 그 밖의 방식은 파랑, 보라, 주황 순서로 칠한다. 같은 색의 연한 색조는 그 대상의 변형이다(`figures/make_paper_figures.py`의 첫 부분).

## 7. 사용법

### 7.1 가중치 in-place

```bash
GGML_CUDA_HOST_PTR=1 llama.cpp/build/bin/llama-completion -m MODEL.gguf -ngl 99 ...
```

- 같은 파일을 매핑한 모든 프로세스가 그 페이지를 공유한다. 서빙 프로세스가
  파일을 쓸 수 없게 유지한다. 파일을 쓸 수 있는 주체는 모든 프로세스의 모델을
  바꿀 수 있다.
- 4 KiB 페이지의 비용을 없애려면 모델을 `huge=always`로 마운트한 tmpfs나
  hugetlbfs에 둔다.
- `GGML_CUDA_HOST_PTR_PREREAD=0`은 CPU가 모든 페이지를 읽는 과정을 생략한다.
- MPS에서는 클라이언트 하나의 GPU 폴트가 같은 서버의 모든 클라이언트를
  종료시킨다. 서로의 장애에서 살아남아야 하는 프로세스는 다른 MIG 인스턴스에
  두거나 MPS 없이 실행한다.

### 7.2 캐시 익스텐트

캐시 변경은 `llama.cpp-kv`를 사용하는 프로세스의 환경 변수로 선택한다.
`LLAMA_KV_HOST`가 없으면 엔진은 원본과 같이 동작한다.

```bash
# 게시자: 프리픽스를 계산한다. 캐시는 파일 /mnt/kv/prefix.0 이다
GGML_CUDA_HOST_PTR=1 LLAMA_KV_HOST=/mnt/kv/prefix LLAMA_KV_GROW=256 \
  ./kv_fork parent MODEL.gguf 8192 prefix.txt prefix.state "" 0
# 에이전트: 앞의 4081행을 읽기 전용으로 매핑하고 그 뒤에 자신의 행을 쓴다
GGML_CUDA_HOST_PTR=1 LLAMA_KV_HOST=/mnt/kv/prefix LLAMA_KV_PREFIX=4081 \
  LLAMA_KV_GROW=256 ./kv_fork child MODEL.gguf 8192 prefix.state "QUESTION" 64
```

| 환경 변수 | 의미 |
|---|---|
| `LLAMA_KV_HOST=anon` | 캐시를 사설 호스트 메모리에 둔다 |
| `LLAMA_KV_HOST=PATH` | 게시자. 캐시는 파일 `PATH.0`이다. 컨텍스트의 상태를 저장하면 사용 중인 행이 게시된다 |
| `LLAMA_KV_PREFIX=ROWS` | 위 변수와 함께 쓰면 에이전트. 앞의 `ROWS`행은 파일의 읽기 전용 매핑이다 |
| `LLAMA_KV_GROW=ROWS` | 메모리가 사용 중인 행을 `ROWS`행 단위로 따라간다 |
| `LLAMA_KV_COW=1` 또는 `2` | 측정 결과가 반대하는 대안. 에이전트가 파일 전체를 쓰기 가능한 사설 매핑으로 매핑한다. `2`는 CPU 읽기를 생략한다 |
| `LLAMA_KV_VMM=1`, `LLAMA_KV_VMM_IMPORT` | `llama.cpp-vmm` 전용. 디바이스 메모리 방식 |

- 게시자의 상태를 저장하면(`llama_state_save_file` 또는 `llama-completion`의
  `--prompt-cache`) 게시된다. 에이전트는 그 상태 파일만 읽을 수 있고, 자신의
  상태를 저장하지 못한다.
- 캐시 파일은 `huge=always`로 마운트한 tmpfs에 두고, 에이전트가 쓸 수 없게
  유지한다.
- 긴 프리픽스를 공유하는 에이전트는 12-SM 인스턴스에 둔다(4.5절).
- 에이전트는 GPU를 사용한 프로세스의 `fork`가 아니라 `posix_spawn`이나 `exec`로
  시작한다.
- 한 프로세스에 둘 수 있는 에이전트는 한 프로세스에 둔다(4.6절).
